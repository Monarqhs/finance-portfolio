# 01. Weekly Digest (Email)

## Status

Draft — awaiting review. Defines the weekly email: how module outputs are
assembled, the layout, delivery, and scheduling. This is the composition point
of the whole pipeline.

## Role

Assemble the outputs of every module into one HTML email sent to the owner each
week. Python builds the **full report with real IDR amounts** (the LLM never
sees these); the narrative layer, if available, provides the opening analyst
note.

## Delivery (carried over from the predecessor)

- **Transport:** Gmail API, OAuth, scope `gmail.send` only (minimal). Reuses the
  predecessor's secret model: `GMAIL_TOKEN_JSON`, `EMAIL_TO`.
- **Schedule:** GitHub Actions cron, weekly (predecessor runs Monday 07:00 WIB /
  00:00 UTC; keep unless the owner changes it). Manual run via the Actions tab.
- **Fail-safe:** a failing section renders a clear note and the email still
  ships; a totally failed run surfaces in the Actions log.

## Email structure

Ordered top-to-bottom so the reader gets the story first, the detail below.

1. **Header** — date, portfolio total value (IDR), week change, and a
   `source` badge showing whether the opening note was written by the LLM or the
   deterministic fallback (transparency).
2. **Analyst note** — the narrative (`docs/02-analysis-specs/05`): market read →
   portfolio read → concentration & opportunities → risks to watch.
3. **Positions & P&L** — per holding: value (IDR), weight %, unrealized P&L,
   and the **asset-P&L vs FX-P&L split**; plus realized P&L to date. (Full real
   amounts — built by Python.)
4. **Portfolio risk** — concentration metrics (sector %, single-factor with
   look-through, HHI), volatility, average correlation, and relative return vs
   benchmark, with the evidence-first flags.
5. **Macro & currency** — rates panel, dollar/VIX, USD/IDR, active regime tags,
   and the non-forecast AI-bubble context block.
6. **Opportunities** — top 2–3 sector-ETF candidates with score breakdown and
   the "candidate to consider, not a buy" limitation.
7. **Signals** — per-holding condition labels with evidence + limitation.
8. **Footer** — data sources, generation timestamp, and a standing disclaimer:
   informational only, not financial advice, no price predictions.

## Rendering rules

- Pure HTML string building (predecessor style), no heavy templating dependency
  unless justified later.
- Every section is independent: if its module returned an error/partial result,
  that section renders its note and the rest proceed.
- Colors/labels reuse the predecessor's convention (green/amber/red) for
  continuity.
- The email is readable on mobile (single-column, legible without horizontal
  scroll).

## Preview mode

A `--preview` flag renders the HTML to a local file without sending (predecessor
parity), so layout can be checked offline during development.

## Test cases

Tests build the email from **fixture module outputs** (no live data, no send).

1. **TC-01 Full assembly.** Given complete fixture outputs for all modules, the
   HTML contains every section (1–8) in order.
2. **TC-02 Section degradation.** With the Macro module flagged as failed, the
   macro section renders its note and sections 3,4,6,7 still render.
3. **TC-03 Source badge.** Narrative `source = "llm"` → badge shows LLM;
   `"deterministic-fallback"` → badge shows fallback.
4. **TC-04 Real amounts only in email, not narrative.** The narrative text block
   contains no real IDR amount; the Positions section does (confirming the
   privacy boundary end-to-end).
5. **TC-05 Disclaimer present.** The footer always contains the "not financial
   advice / no predictions" disclaimer.
6. **TC-06 Preview writes file, does not send.** `--preview` produces the HTML
   file and makes no Gmail API call.
7. **TC-07 Empty portfolio.** With no open positions (all closed), the email
   renders gracefully (realized P&L only) without errors.
8. **TC-08 Mobile single-column.** Rendered HTML uses a single-column layout
   (no multi-column table that forces horizontal scroll) — asserted structurally.
